## 3. D2 — Relationship/memory-influences-later-decision: the required scenario

One pinned scenario, reusing existing mechanisms only (no new weight math, no new candidate source):

1. Build a two-colonist state where colonist A has two roughly-equal-weight voluntary candidates available at the same tier: a `conversation` candidate toward colonist B, and one unrelated candidate with no relationship tie (e.g., an idle/self-serving candidate).
2. Drive several real ticks of `run()` (not hand-constructed state) that produce a large, unambiguous relationship shift toward B in one direction — the simplest, already-existing lever is repeated Shared Downtime/Conversation ticks (positive drift) or one hand-authored `applyInteraction` call with a large magnitude before the decision tick (matching the existing hand-built-fixture pattern `tick.test.ts` already uses for Confrontation's `workstationPairState`).
3. Assert that `decide()`'s chosen candidate for A changes between the "before" and "after" relationship states, all else held equal — i.e., the relationship-toward-B tilt was large enough to flip the selected candidate, not merely to nudge its weight. This is the acceptance criterion's own bar ("demonstrably affect later candidate weights / decisions"), not a mere unit-level weight-composition check (already covered).
4. **Memory-driven flip uses its own, different candidate pair — it cannot reuse step 1's.** `decision/weights.ts`'s `memoryContributions` (line ~46) filters strictly to `entry.type === "deprivation"` matching the candidate's own `relatedNeed`. Step 1's `conversation`/idle pair (`goals.ts`'s voluntary-candidate generation, lines ~122-150) carries no `relatedNeed` at all, so *no* memory — deprivation or relational — could ever tilt either of them; reusing that pair here would make the scenario structurally unsatisfiable regardless of which memory type is used. The memory scenario is therefore built from two same-tier `lowNeed` candidates with distinct `relatedNeed` values instead (e.g., `hunger` and `safety` — both biological/psychological `lowNeed`-tier candidates already generated by `goals.ts`'s existing lowNeed path, `relatedNeed: id`), roughly equal weight before the memory forms. Separately, a **relational** memory (the only kind a Confrontation/Shared Downtime/Comfort interaction can form) cannot reach candidate weighting at all today regardless of candidate shape — production code that is out of this test-only slice's scope to change. The required scenario is therefore satisfied with the memory type the weighting mechanism actually reads: force a `memoryFormed` (deprivation, matching one candidate's `relatedNeed`) event via a real tick, then run a later decision tick over this two-need-candidate pair and assert the before/after candidate-selection change, citing `influence()`'s fade curve so the test picks a "later" tick still within the memory's non-negligible influence window (per `memory-system.md`/ADR-16's fade model). A second, explicitly named test pins the gap itself — a relational memory formed via a real tick produces no candidate-selection change — so a future slice cannot let this drift silently. Widening `memoryContributions` to read relational memories is a production change and its own separately-authorized card, not this plan's to make.

## 4. D3 — Save/load continuation, mid-action

Four save points, each taken mid-action, each continued and compared against an uninterrupted run of the same total length (reusing `continueRun`'s existing contract, `main.test.ts`'s own pattern):

1. Mid-pending social offer (any offer-backed action, respondable but not yet resolved).
2. Mid-accepted-Comfort execution (the initiator/comforter mid-`comfort` execution; the recipient/responder holds no Comfort goal or execution of their own — per `design/comfort-assist-protocol.md` v0.4.0, "Comfort never writes the responder's execution slot" — and participates only via the Social/stress/relationship consequences applied directly to their state).
3. Mid-`In Conflict` window (`inConflictUntilTick` in the future relative to the save's own clock).
4. Mid-suspended-goal (an existing Slice 6 scenario, included for completeness against the full current field set — not new).

**Assertion shape (superseded once, by v0.3.1 — see below):** each save point is continued and compared against an uninterrupted run of the same total length via `continueRun`'s existing contract. No new save/format field, no new invariant — this is exercising the existing contract against a fuller set of starting states than today's generic pick.

**v0.3.1 correction — `main.test.ts`'s literal `continued.save === uninterrupted.save` comparison is not usable for any of these four save points, for a reason outside this plan.** Implementation found that `serialize()` is not byte-stable across a load round trip once a colonist holds memories: it is `JSON.stringify`, so it records key *insertion* order, and `deserialize()` rebuilds a `MemoryEntry` in a different key order than `memory.ts` uses when forming one live. The states are identical (`toEqual` passes) and `verifyReplay` matches; only the encodings differ. **This supersedes the literal-string requirement entirely for this slice — it is not an exception carved out for some save points and not others.** Slice 9's four mid-action continuation tests therefore each assert, in place of `continued.save === uninterrupted.save`: `continued.summary` equals `uninterrupted.summary`; the **decoded** state (`deserialize(continued.save)` compared to `deserialize(uninterrupted.save)`) is equal; and `verifyReplay`/`verifySaveReplay` reports a match. This is what "reaches the same state" means once the encoding defect is accounted for. The encoding defect itself is pinned by its own separately named test (not folded into the four continuation tests) and tracked as issue #163; when it is fixed, the literal save-string comparison becomes usable again and should be restored across all four save points.

## 5. D4 — Replay: event log, decision log, terminal-state match

One fixed-seed, multi-colonist run long enough to plausibly exercise Conversation, Shared Downtime, Shared Meal, Comfort (accepted at least once), and Confrontation (fired at least once — reusing the existing seed-hunt pattern from `tick.test.ts`'s Confrontation block) in a single trace. Assert:

- `verifySaveReplay`'s existing match/mismatch contract returns `"match"` for this run (reusing `main.test.ts`'s own `demoRun(...).replay.kind === "match"` pattern, not inventing a new verification path).
- The event log and decision log reproduce byte-identically across two independent `tick()`/`run()` invocations from the same initial state and seed (the same double-run-and-compare pattern `tick.test.ts`'s Confrontation "replay determinism" test already uses).
- Terminal state matches via the existing generic `STATE_FIELDS` diff (`replay.ts`), asserting zero divergent fields.

This does not require a new replay mechanism — it is one integration-scale exercise of mechanisms already proven generically, run across the actual current action set together for the first time.

## 10. Test matrix (concrete additions this plan specifies)

**Comfort — real-run consequences (closes the headline gap, §2)**
- An accepted Comfort execution (the initiator/comforter committed and executing `comfort`; the recipient/responder receiving the consequences directly, without a Comfort goal or execution of their own — `design/comfort-assist-protocol.md` v0.4.0's D5: "Comfort never writes the responder's execution slot") run to completion via real `tick()`/`run()` calls applies the `positiveSocialProximity` stress relief to the recipient, decomposable in a `stressEvaluated` event.
- The same run credits `comfortSocialRestorePerTick` of Social to **both** participants, initiator and responder, per `design/comfort-assist-protocol.md` v0.4.0 §9/D7's Social row (ADR-18 D7's "Participation credits…") — confirmed by a real trace, not just design-doc assertion. The mirrored non-effect belongs to the *declined / cancelled / expired* path (§9's Non-effects list) and is asserted separately, as **two distinct cases**, verified directly against `tick.ts`'s actual resolution paths (`tick.ts:1006-1046`): a Comfort offer that resolves via `declineWithFriction` (`responderNotInterruptible`/`relationshipGate`/`acceptanceDraw`) restores no Social to either party and applies the existing negative-affinity decline friction (`applyInteraction` is called); a Comfort offer that resolves via `"cancelled"` or `"expired"` (`initiatorUnavailable`/`responderUnavailable`/`timeout`) restores no Social **and applies zero affinity movement in either direction** — `tick.ts`'s `resolved(...)` path for those two statuses never calls `applyInteraction` at all. These are not the same assertion and must not be tested as one.
- Neither participant is ever credited Purpose, accepted or not (ADR-17 D6 / ADR-18 D7's distinctness constraint).
- The same run forms a relational memory for at least one participant when ADR-16's significance criteria are met (or documents, per §2 above, why a smaller-magnitude interaction did not — this test must use a magnitude clearly above the threshold, not rely on Comfort's smallest possible tuning).
- A second Comfort claim naming the same recipient while the first is still active is rejected by `validateSimulationState`'s existing one-comforter invariant, exercised through a real tick rather than only the direct unit call already in `comfortParticipation.test.ts`.

**`Socializing` ambient — real-run reachability (closes the §2 gap; required by Issue #160's own acceptance criteria, not optional)**
- Run at least one of Conversation, Shared Downtime, or Comfort to an accepted, in-progress execution via real `tick()`/`run()` (reusing `tick.test.ts`'s existing accepted-offer fixture pattern, e.g. `pendingOfferState`, rather than a new harness), then assert `ambientStateFor`'s real output for the participant(s) — via `inspect(...).colonists[*].ambientState` or the equivalent direct call already used elsewhere in the suite — reads `"socializing"`, not merely that the offer/execution status transitioned.
- Extend `execution.test.ts`'s own "maps each in-progress task to its ambient state" unit test (currently working/eating/resting/blocked only) with the three `socializing`-mapped tasks (`conversation`, `sharedDowntime`, `comfort`) as a cheap, direct companion to the real-run assertion above — this closes the gap at both the unit and real-run layers, matching how `inConflict` is already covered at the real-run layer by Confrontation's own test.

**Relationship/memory → later decision (§3)**
- Two tests, over two different candidate pairs: one relationship-driven candidate-selection flip (§3 steps 1-3, the `conversation`/idle pair); one memory-driven candidate-selection flip using a deprivation memory over two same-tier `lowNeed` candidates with distinct `relatedNeed` values (§3 step 4's correction — `memoryContributions` keys on `relatedNeed`, which the relationship pair's candidates never carry, so the memory scenario needs its own candidate pair, not a reuse of step 1's).
- One additional, explicitly named test pinning the relational-memory gap: a relational memory formed via a real tick produces no candidate-selection change today.

**Save/load, mid-action (§4)**
- Four tests, one per save point listed in §4, each asserting `continueRun` parity with an uninterrupted run via decoded-state equality, summary equality, and replay match (per §4's v0.3.1 correction — not literal save-string equality, which issue #163's encoding defect currently blocks).
- One separate, explicitly named test pinning issue #163 itself (the `serialize()`/`deserialize()` key-order mismatch for `MemoryEntry`) — not folded into the four continuation tests above.

**Replay, multi-action (§5)**
- One fixed-seed multi-action integration run asserting `"match"` replay verification, byte-identical double-run event/decision logs, and zero `STATE_FIELDS` divergence.

**Inspector (§6)**
- Three parametrized additions to existing `inspector.test.ts` describe blocks (mid-Comfort/mid-inConflict detachment, Confrontation-shifted pair, Comfort offer lifecycle) — no new inspector code.

**Regression (unmodified, must stay green)**
- Every existing Slice 5–8 test file listed in §2's table, full `prototype/src` suite, strict TypeScript.

## 11. Findings and ambiguities requiring Human decision

1. **Assist checkbox wording (§9/D8).** Flagged for Human ruling before Issue #119 can close, or before this slice's own acceptance criteria can be marked fully met. **Resolved (v0.3.1 note):** Human ruled Option A on Issue #160 — named deferral satisfies parent #119; recorded when PR #161 was approved and merged. This plan prefers hand-authored magnitudes and flags the seed-hunt fallback as a lower-preference option for Cursor to justify if hand-authoring cannot be made to work.
4. **Whether Confrontation's provisional `directConflictAffinityDelta` clears ADR-16 significance** is a real open question (DQ-4) this plan's own memory-flip scenario may surface concretely for the first time — if it does not, this is calibration feedback for Confrontation's own deferred tuning, not a defect in this plan.
